# Architecture Decision Records

## ADR-001: .NET WPF 선택
**결정**: Windows 데스크톱 앱은 `.NET WPF`로 구현한다.

**이유**:
- 실제 USB CAN 장비 SDK(Kvaser CANlib, PEAK PCAN-Basic)와 연동하기 쉽다.
- 양산 현장 Windows PC에서 장시간 운용하기 적합하다.
- MVVM 구조로 UI와 통신/진단 계층을 분리하기 좋다.
- WinForms보다 현대적인 UI를 만들 수 있고, Electron보다 네이티브 장비 연동 부담이 작다.

**트레이드오프**:
- 웹 UI 대비 스타일링 생산성이 낮을 수 있다.
- 최신 UI 느낌을 내려면 공통 스타일 시스템과 컴포넌트를 의도적으로 설계해야 한다.

## ADR-002: MVVM + 계층형 아키텍처
**결정**: `App`, `Application`, `Domain`, `Infrastructure` 계층으로 분리한다.

**이유**:
- UI가 CAN Driver나 UDS parsing을 직접 알면 유지보수가 어려워진다.
- Kvaser/PEAK/Simulator 교체 가능성을 보장해야 한다.
- 자동검사, 수동 진단, 리포트 생성은 UI와 독립적으로 테스트되어야 한다.

**트레이드오프**:
- MVP 초기 코드량은 단순 단일 프로젝트보다 많다.
- 인터페이스와 DTO 설계가 필요하다.

## ADR-003: 실제 Kvaser/PEAK USB CAN 장비 지원
**결정**: MVP에서 실제 Kvaser/PEAK USB CAN 장비 인식과 실제 UDS 송수신을 필수로 한다.

**이유**:
- EOL 프로그램은 실제 장비와 제품을 검사해야 의미가 있다.
- Simulator만으로는 양산 사용성을 검증할 수 없다.
- 장비 연결/해제 상태가 모든 화면에 표시되어야 한다.

**트레이드오프**:
- 개발/테스트 환경에 Vendor SDK와 실제 장비가 필요하다.
- 장비별 오류 처리와 배포 검증이 추가된다.

## ADR-004: CAN Setting은 설정 영역에 둔다
**결정**: CAN Setting은 기능 메뉴가 아니라 설정 영역에 둔다. 검사 준비 화면에서는 장비 상태만 표시하고, 필요 시 설정으로 이동할 수 있게 한다.

**이유**:
- CAN Setting은 EOL 기능이 아니라 config 성격이다.
- 작업자 화면에서 세부 CAN 설정을 과도하게 노출하면 혼란과 실수 가능성이 커진다.
- 장비 미연결 시에는 설정으로 이동할 수 있어야 한다.

**트레이드오프**:
- 검사 준비 화면에서 모든 설정을 한눈에 볼 수는 없다.
- 문제 분석 시 설정 화면으로 이동해야 한다.

## ADR-005: DTC Excel 원본 + JSON 실행 파일
**결정**: DTC 매핑은 Excel을 원본 관리 파일로 두고, 앱은 JSON을 실행 파일로 읽는다.

**이유**:
- Excel은 사람이 검토하고 관리하기 좋다.
- JSON은 앱에서 빠르고 안정적으로 로드하기 좋다.
- WPF 앱이 Excel 파일을 직접 파싱하면 형식/라이브러리/성능 문제가 늘어난다.

**트레이드오프**:
- Excel과 JSON 사이의 변환/검증 절차가 필요하다.
- 두 파일이 불일치할 가능성이 있으므로 이후 변환 도구가 필요하다.

## ADR-006: 자동검사에서 DTC 판정 분리
**결정**: 수동 DTC 조회에서는 DTC 존재가 NG가 아니며, 자동검사에서는 고장 소거 후 과거 DTC가 남아 있으면 NG로 판정한다.

**이유**:
- 수동 현재/과거 고장 진단은 조회 기능이다.
- 조회 기능의 통신 성공 여부와 제품 출하 판정은 다르다.
- EOL 자동검사는 판매 가능한 새 제품 상태로 만들고 검증하는 절차이므로 고장 소거 후 DTC가 남으면 실패로 보는 것이 맞다.

**트레이드오프**:
- 같은 과거 고장 조회라도 수동 화면과 자동검사에서 의미가 다르므로 UI 문구가 명확해야 한다.

## ADR-007: 리포트는 PDF + 내부 JSON으로 저장
**결정**: 검사 결과는 저장 전 미리보기로 표시하고, 저장 시 PDF와 내부 JSON을 생성한다. HTML 파일은 저장하지 않는다.

**이유**:
- PDF는 현장 보관, 공유, 출력에 적합하다.
- JSON은 결과 리포트 조회, 검색, 재출력, 분석을 위한 내부 원본 데이터다.
- HTML은 화면 미리보기에는 좋지만 파일 산출물로 관리할 필요는 낮다.

**트레이드오프**:
- JSON을 사용자에게 직접 보여주지는 않지만 저장 공간이 추가로 필요하다.
- PDF 생성 실패 시 JSON 기반 재생성 흐름이 필요하다.

## ADR-008: ProgramData 아래 제품 데이터 관리
**결정**: 앱 설정, 매핑, 리프로 파일, 리포트, 로그는 `C:\ProgramData\DaedongRobotics\EolDiagnosticTester` 아래에서 관리한다.

**이유**:
- Windows에서 장비 공용 데이터 저장 위치로 적합하다.
- 사용자 계정과 무관하게 설정과 리포트를 유지할 수 있다.
- 기존 사용 경로와 호환된다.

**트레이드오프**:
- 설치/실행 권한에 따라 폴더 생성과 쓰기 권한 확인이 필요하다.

## ADR-009: 통신 모니터링은 Trace 중심 MVP
**결정**: 통신 모니터링은 공통 도구로 두고, MVP에서는 CAN Trace만 제공한다. Manual Transmit은 제외한다.

**이유**:
- EOL 핵심 기능은 자동검사와 진단이다.
- Trace는 문제 분석에 필요하지만 송신 기능은 ECU에 영향을 줄 수 있다.
- PCAN-Explorer/Vector처럼 빠르고 안정적인 trace 표시가 우선이다.

**트레이드오프**:
- 개발자용 수동 송신은 MVP에서 사용할 수 없다.
- 필요 시 이후 관리자 기능으로 확장해야 한다.

## ADR-010: 현대적인 WPF UI
**결정**: UI는 Windows 11/Fluent 스타일의 현대적 산업용 데스크톱 앱으로 설계한다.

**이유**:
- 현장 작업자가 세련되고 편리하다고 느낄 정도의 품질이 필요하다.
- 구시대적인 테이블/버튼 나열식 UI는 사용성이 떨어진다.
- 상태 배지, 결과 패널, 정돈된 테이블, 명확한 진행 표시가 검사 효율을 높인다.

**트레이드오프**:
- 공통 스타일과 컴포넌트 설계가 필요하다.
- UI 구현 시간이 단순 기본 WPF 컨트롤 사용보다 늘어날 수 있다.
